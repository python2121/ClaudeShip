# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ClaudeStatus` is a single-target Swift Package macOS menubar app (`Package.swift`, `Sources/ClaudeStatus/`). It shows one glyph in the menubar summarizing all running Claude Code sessions — a **green ◐◓◑◒-style spinner** (0.25 s/frame, timer runs only while busy) when any session is busy, an **orange ●** when one or more are waiting on user input, and **○** in the system label color when everything is idle (or nothing runs). The glyphs are **drawn with NSBezierPath, not font characters** — the system font lacks U+25D0–25D3, and fallback served the left/right halves and top/bottom halves from different fonts at visibly different sizes. Don't switch back to string glyphs. Clicking it opens a borderless overlay panel listing each session (project, branch, path, state + how long it's held, uptime). The menubar app itself is local inspection: no network, no keychain, no credentials. The one thing that listens on the network is the separate **session hub** process (below), and only to loopback and the tailnet.

The build scripts, panel machinery, and visual style are lifted wholesale from `~/Documents/code/claude-usage` (ClaudeUsage) — same borderless `NSPanel` + `NSVisualEffectView` chrome, same animations, same footer idiom. The overlay is **392 pt wide** (vs ClaudeUsage's 280); height follows the SwiftUI content. When restyling, keep the two apps visually in sync.

## Common commands

```bash
./build-app.sh                    # swift build -c release + assemble + codesign → ./ClaudeStatus.app
./install.sh                      # build (unless SKIP_BUILD=1), replace /Applications/ClaudeStatus.app, restart
swift run ClaudeStatus --self-test  # run the hand-rolled test suite (exit 0/1)
swift run ClaudeStatus --scan       # headless: print detected sessions and exit — debug the heuristics
swift run ClaudeStatus --focus <pid> # headless: raise that session's terminal, print host app/title/outcome
swift run ClaudeStatus --host <pid>  # headless: print every app in <pid>'s ancestor chain and which one the walk picks
swift run                          # dev loop (menubar app, unsigned)
swift run ClaudeStatus --cli hub status  # dev build of the `claudeandrew` command (everything after --cli is its argv)
```

## Architecture

`App.swift` → `AppDelegate.swift` → `SessionStore` (single source of truth) drives an `NSStatusItem` and a borderless `PopoverPanel` hosting `SessionsView` (SwiftUI). `SessionStore` polls every 2 s (cheap — all local); `objectWillChange` is observed by `AppDelegate` to repaint the menubar count (hop one runloop tick because `objectWillChange` fires *before* the `@Published` write).

Detection path — `SessionScanner.swift`, all pure/blocking, called off-main via `Task.detached`:

1. **Live-session registry (the source of truth)** — Claude Code maintains one JSON status file per running process at `~/.claude/sessions/<pid>.json` with `pid`, `sessionId`, `cwd`, `name` (e.g. "claude-status-b3"), `startedAt`/`statusUpdatedAt` (epoch **ms**), and an authoritative `status`. The CLI's status enum (extracted from the 2.1.202 binary) is `["busy","shell","idle","waiting"]`, plus a `waitingFor` detail string. Mapping: busy→green work, shell→user running a `!` command, idle→at the prompt (NOT an alarm state), waiting→orange. Unknown/missing statuses read as idle — never a false alarm color. Files whose pid is dead (`kill(pid, 0)`) are crash leftovers, skipped. The rust app at `~/Documents/code/system-stats` (`src/claude.rs`) reads the same registry and was the reference for this.
2. **Transcript garnish** — the transcript at `~/.claude/projects/<dashed-cwd>/<sessionId>.jsonl` (cwd flattens: every non-alphanumeric/`-` char becomes `-`) is tail-read only for `gitBranch` and mtime. State never comes from transcripts: a first cut inferred it from the last JSONL entry and couldn't distinguish "idle at prompt" from "waiting on permission" — don't regress to that.

`SingleInstance.swift` (flock on `~/Library/Application Support/ClaudeStatus/instance.lock`) guards against duplicate menubar items, same rationale as ClaudeUsage. `--permission-hook`, `--install-hook`/`--uninstall-hook`, `--self-test`, `--scan`, `--focus <pid>`, and `--host <pid>` dispatch at the top of `App.main`, before NSApplication or the lock.

## Session hub (`claudeandrew` + the web app)

A second process, built from the same binary, that **owns the pty of every Claude session started through it** — so a session outlives whichever terminal or browser is looking at it, and any number of screens can attach to the same one. tmux's shape, but raw passthrough: the hub never re-renders the screen, it relays bytes, so the local terminal keeps its own scrollback, key handling, and features.

- **One binary, two names.** `build-app.sh` copies the executable to `Contents/MacOS/claudeandrew`; `App.main` dispatches on `argv[0]` (or `--cli` in a dev build) to `HubCLI` before any flag checks, because under that name every argument belongs to claude. The copy is deliberate: the hub's process name must not be `ClaudeStatus`, or `install.sh`'s `pkill -x ClaudeStatus` would kill the hub and every session with it. **The hub is never restarted by an install** — it keeps running the old build until `claudeandrew hub stop`.
- **`claudeandrew [args]`** (`HubCLI.swift`) asks the hub to spawn `claude args` in the caller's cwd with the caller's environment, then becomes a dumb pipe: raw-mode stdin up, output bytes down, SIGWINCH as resize frames. Closing the terminal only detaches. Invocations that aren't a session to share exec claude directly (`bypassesHub`, tested): `-p`, `--version`, `--bg`, claude's management subcommands (`mcp`, `update`, …), or stdio that isn't a tty. The hub auto-starts on first use (detached with `POSIX_SPAWN_SETSID`, log at `hub/hub.log`); `claudeandrew hub status [--json]|link|unlink|start|attach <id>|kill <id>|stop` manage it. **Resume semantics:** `claudeandrew --resume <uuid>` of a conversation that is already running in the hub attaches to it instead of starting a copy (`resumedSessionId`/`hubSession(forClaudeSessionId:)`); `hub attach` takes a Claude session UUID as well as a hub id; `hub status --json` joins each hub session to its registry entry (`sessionId`, `claudePid`, `status`, `title`) — the integration surface for other tools (system-stats).
- **Hub** (`Hub.swift`, `HubPTY.swift`): all state on one serial queue. Sessions are spawned with `posix_spawn` (not forkpty — fork in a multithreaded Swift process); `POSIX_SPAWN_SETSID` + opening the pty slave as fd 0 gives the controlling terminal. The session leader is **`HubSupervisor`** (this binary, `hub supervise`), which runs claude as its foreground job and answers a stop with SIGCONT. Claude can't lead the session itself: a leader with no parent in its session is an orphaned process group, the kernel discards its SIGTSTP, and Claude's Ctrl+Z handler (cooked mode, "run `fg`", stop self) would strand the session half-suspended — verified against 2.1.289. So a hub session's pid is the supervisor, and `HubState` matches it to the registry session nearest below it in the process tree. The supervisor forwards SIGHUP/SIGTERM/SIGINT to the program and exits only when it does, so the exit code the hub reports is the program's and `finished` means it is really gone; Input to the pty is written non-blocking and the remainder retried on a 3 ms timer — not a write-readiness source, which does not fire reliably for a pty master on macOS (an 8 KB paste stalled after the first kilobyte). `terminate` hangs up the supervisor only (one SIGHUP reaches the program); after 5 s it sends SIGTERM, which the supervisor answers by SIGKILLing its job, then SIGKILLs both groups. Sessions that ended in the last 30 s are kept (`ended`) so a late attacher still gets the output and exit code of a launch that failed at once. Unix socket at `~/Library/Application Support/ClaudeStatus/hub/hub.sock`, framed protocol in `HubProtocol.swift`. `CLAUDEANDREW_HOME` relocates the socket/lock/log/config/token, `CLAUDEANDREW_CMD` swaps claude for a stand-in, `CLAUDEANDREW_WEB` points at the web assets — together they give tests a private hub (note the 104-byte `sun_path` limit: the scratch dir must be short).
- **Attaching late** is the hard part, and `TerminalStream`/`ReplayBuffer` (`HubProtocol.swift`, heavily self-tested) are the answer. Every output byte is tokenized by escape sequence; the hub tracks the terminal modes the program has set (alt screen, mouse, bracketed paste, kitty keyboard stack…) and keeps a bounded replay copy with the things that must not happen twice removed — **terminal queries** (a replayed query makes the new terminal answer into claude's stdin), OSC 52 clipboard writes, notifications, bells. A new client gets `restoreSequence` for the modes in force at the buffer's start, then the buffer. `ESC[2J`+`ESC[3J` on the main screen resets the buffer. The terminal client runs the same tracker so it can undo those modes if it leaves before the program does.
- **One pty, one size**: the client that attached, typed, or resized most recently owns the size (`claimSize`). "Typed" means the person did something — `TerminalInput.isUserActivity` (tested) excludes what terminals send on their own (query answers, focus reports, bare pointer motion), or two attached screens answering the same query would take the size from each other forever. Browsers are told the size and adapt (scale the foreign size to fit, offer "Fit here", report their own fit with `fit` so a later keystroke claims the right size, and rejoin with `claim=0` after a dropped connection so they don't reflow the session). A terminal client can't be told anything: until someone types there it shows output laid out for the other screen. Every attached terminal also answers the program's live queries, so claude can receive an answer per screen — harmless so far, and not worth diverging the byte streams to prevent.
- **Builds drift apart on purpose**: the hub is never restarted by an install, so a new `claudeandrew` or a new page (assets are read from disk per request) can meet an old hub. `HubFrame.version` is stated in the hello frame, `hub status`, and `/api/state` (`PROTOCOL` in `web/app.js` must match); launch/attach across versions is refused with instructions, the page shows a banner. Bump it whenever either side would misread the other. One thing an old hub does *not* keep: it spawns each session's supervisor from the installed bundle path, so after an install new sessions get the new supervisor (and a launch during the install's rm/cp window fails with 127). A dev-build hub runs as `ClaudeStatus --cli …`, so `install.sh`'s pkill does take it down — use `CLAUDEANDREW_HOME` for dev hubs.
- **Web** (`HubWeb.swift`, static files in `web/`, served from `Contents/Resources/web` or the repo's `web/` in a dev build): hand-rolled HTTP/1.1 + WebSocket on Network.framework, port 7433 (`hub/config.json`: `port`, `root`, `defaultPermissionMode`). `GET /api/state` is the directory (`HubState.build`: folders under `root` = projects, registry sessions matched to hub sessions by pid, recent `ai-title`s per project, ordering per `HubState.order`); `POST /api/launch|kill|settings` (new sessions default to `--permission-mode auto`); `/ws/term?id=` is a terminal attachment (binary frames = pty bytes, text frames = JSON control). Web launches run `claude --permission-mode <mode>` under the user's login shell (`-l -i`) with a whitelisted environment, since there is no terminal to inherit one from. The page is plain JS + vendored xterm.js, no build step, and builds DOM with `textContent` only — titles are untrusted text and this page is a shell.
- **It is a remote shell, so the gate matters** (`HubWebSecurity`, `HubToken`; self-tested). Three independent checks, all required: (1) **network** — loopback talks only to loopback; otherwise the local address must be one a `utun` interface actually holds *and* both ends must be in Tailscale's ranges (100.64.0.0/10, fd7a:115c:a1e0::/48). The range alone is not enough: it is ordinary CGNAT space that some Wi-Fi networks hand out. (2) **Host header** — only `localhost` and loopback/tailnet IP literals, never a DNS name: over plain HTTP whoever runs the network's DNS can answer any name (including this Mac's own, or a `.ts.net` one) with their server and then with 127.0.0.1, and their page would be same-origin with us, cookie included. `allowedHosts` in `hub/config.json` is the exact-match escape hatch (e.g. for `tailscale serve`). (3) **pairing secret** — a random token in `hub/token` (0600), presented once via `claudeandrew hub link` (prints the `/auth?k=` URLs and a QR code for the phone) and held from then on as an HttpOnly SameSite=Strict cookie; every `/api/*` request and the WebSocket need it. Network position is not a login — other users of the Mac, a sandboxed app, or a forwarded port all reach 127.0.0.1. Nor is the tunnel check Tailscale-specific: other mesh VPNs (WARP, NordVPN Meshnet) also put 100.64/10 addresses on `utun`, and their peers pass check (1); the secret is what stops them. On top: on the WebSocket upgrade and on POSTs any `Origin` must be our own (WebSockets ignore the same-origin policy), POSTs must be JSON, connections are capped and swept when stalled. The cookie is scoped to the host, not the port, so other servers on `localhost` see it; `claudeandrew hub unlink` rotates the secret. Don't loosen any of these without replacing it with something stronger.
- Sessions started directly in a terminal (plain `claude`) still appear in the web directory with live status, but can't be attached to ("Terminal only") — nothing can take over a pty it doesn't own.
- In the menubar overlay, hub sessions (`ClaudeSession.hubId`, matched by the hub's supervisor pid in the ancestor chain via `HubCLI.liveSessions()`) group under a **Virtual** header between real hosts and Background; clicking one opens a new terminal window running `claudeandrew hub attach <id>` (`TerminalFocus.openTerminal`, shared with the Background path). Right-clicking any row offers **End session** (`AppDelegate.endSession`): hub sessions through the hub's `kill` op (`HubCLI.endHubSession`), others by SIGHUP to the pid with SIGKILL after 5 s if the registry file is still there. The web page returns to the directory on its own when a session ends, with a banner saying so. `--scan` prints `hub=<id>` on those rows.
- Not done yet: the hub does not start at login.

## Remote approval (the PermissionRequest hook bridge)

When a session hits a permission prompt, the user can approve/deny it from the overlay instead of the terminal. Three pieces:

1. **Hook** — `install.sh` runs `--install-hook` automatically (`SKIP_HOOK=1` opts out), which registers a `PermissionRequest` hook in `~/.claude/settings.json` (command: the `/Applications` binary + `--permission-hook`, timeout 86 400 s — a leak backstop, not UX; see below). The merge (`HookInstaller`) is surgical and idempotent; it only ever touches the one entry containing the `--permission-hook` marker.
2. **Helper** (`PermissionHook.swift`) — spawned by Claude Code with the request JSON on stdin (`tool_name`, `tool_input`, `session_id`, `cwd`). It forwards one request line over the UDS socket at `~/Library/Application Support/ClaudeStatus/approvals.sock` and blocks **with no deadline** for a verdict — the terminal prompt is live concurrently, so blocking hides nothing, and the app hangs up (EOF) when the prompt resolves elsewhere. **The prime directive: emit a decision only on an explicit verdict.** App not running, hang-up, crash, malformed reply — all exit 0 with no output, which Claude Code treats as "no decision" and defers to the terminal prompt. Output schema (verified against the CLI's own zod validator): `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"|"deny"}}}`.
3. **Server** (`ApprovalCenter.swift`) — blocking POSIX UDS server inside the app; one connection = one pending approval. `SessionStore` publishes `pendingApprovals`, matches them to session rows by `sessionId`, and forces those rows' effective state to waiting. If a helper dies anyway, `onClosed` drops the buttons instantly so a stale click can't fire into nothing. Pendings with no matching live session (session exited, ids never lined up) are pruned after a 10 s grace period (`shouldPruneUnmatched`) — with no helper deadline, that prune is what prevents immortal requests.

**The terminal prompt and our buttons are live simultaneously** — the CLI renders its prompt while the PermissionRequest hook is still running, and whichever side answers first wins. That requires reconciliation for the terminal-wins case: while the prompt is up, the session's registry status reads `waiting`; answering it flips the status (usually to `busy`) with a fresh `statusUpdatedAt`. Each poll, `reconcilePendingWithRegistry()` drops any pending approval whose session left `waiting` with a status change newer than the approval's arrival, and closes its helper connection via `server.cancel(id)` — a verdict-less shutdown (distinct from `respond`) so we never answer a question the terminal already settled. The predicate (`resolvedInTerminal`) is deliberately conservative: the pre-prompt `busy` state has a *stale* `statusUpdatedAt`, so it can't false-trigger at arrival.

The overlay renders Approve / Deny / `⋯` **in place of the status text** on the affected row, with the command summary where the timing caption goes. The `⋯` menu holds "Approve all for 5 minutes" and "Approve all for this session" — per-session auto-approve rules held in memory only (deliberately not persisted; a standing approval shouldn't outlive the app that granted it), pruned when they expire or the session ends, and marked with a yellow bolt on the row.

## Click-to-focus (raising the session's terminal)

Clicking a row brings that session's terminal to the front (`TerminalFocus.swift`, wired through `SessionsView.onFocusSession` → `AppDelegate.focusTerminal`, which closes the panel first and runs the focus off-main on a serial queue). Two tiers:

1. **Emulator adapters**, chosen by the bundle id of the host app: `hostApp` walks the sysctl `ppid` chain (claude → zsh → login → Ghostty) collecting every ancestor LaunchServices knows as an app and prefers the nearest one with a *regular* activation policy (`chooseHostIndex`, tested), settling for an accessory only when nothing regular is above it. Verified against VS Code: its helpers (`Code Helper (Plugin)` etc., all `com.microsoft.VSCode.helper`, LSUIElement) don't register with LaunchServices at all, so the walk lands on `com.microsoft.VSCode`; the policy preference guards against editors whose helpers do register. **Ghostty 1.3+** has an AppleScript dictionary but exposes no pid/tty, so surfaces are matched on working directory plus the tab title Claude Code sets — the transcript's newest `ai-title` entry, which the scanner now reads alongside `gitBranch` and the store carries forward (`ClaudeSession.title`). Match order: cwd + title, title alone, cwd alone, else fall through. One list round-trip (`ghosttyListScript`), the pick in Swift (`pickGhosttyTerminal`, tested), then `focus terminal id "…"`. **Terminal.app** and **iTerm2** expose a `tty` per tab/session, matched to the pid's controlling tty (`ttyPath`, via `kinfo_proc.e_tdev` + `devname`).
2. **VS Code bridge** (`vscode-extension/`, adapter `.vscode` for VS Code / Insiders / Cursor / VSCodium bundle ids). VS Code has no scripting for terminals, so a vendored extension (plain JS, no build) runs in every window and watches `~/Library/Application Support/ClaudeStatus/vscode-focus/request.json`. The app writes `{ts, nonce, pids, cwd, sessionId}` there atomically (`bridgeVSCode`), where `pids` is the session pid's whole ancestor chain (`ancestorPids`); each window compares its terminals' `processId` (the shell pid) against that list — only the owning window matches, which is what makes one shared file work across windows and across several claudes in one window. That window calls `terminal.show()` (selects the exact tab/split) and answers `reply.json` with `{nonce, workspace, terminal}`; the app then raises that window with the editor's bundled CLI (`cliURL`: `<cli> <workspace>` focuses the window that already has it open, never opens a new one), or plain activation when the reply has no workspace (untitled window). No reply within 1.5 s (extension missing, remote window, no match) falls through to tier 3. The extension ignores requests older than 15 s and dedupes by nonce. It also publishes each window's state to `vscode-focus/windows/<env.sessionId>.json` (`{ts, name, workspace, terminals:[{pid,name}]}`) on activation, terminal open/close, and a 30 s heartbeat, removing it on deactivate; the scanner loads those once per scan (`loadVSCodeWindows`, files older than 90 s ignored) and `TerminalFocus.host(of:windows:)` resolves each session's `SessionHost` (app + VS Code window label). `install.sh` packages it with `vscode-extension/pack.sh` (zip + vsix manifest, no npm — a symlink into `~/.vscode/extensions` is *not* picked up) and installs via each editor's CLI that exists on disk; `SKIP_VSCODE_EXT=1` opts out; open windows need one reload after an install. Same folder open in two windows resolves to whichever the CLI picks — the only known inexact case.
3. **Generic fallback**: activate the host app (`NSRunningApplication.activate()`, then `NSWorkspace.openApplication` with `activates` — the cooperative `activate()` can be refused because our panel is non-activating). Right app, whatever tab it was on. Kitty/WezTerm/tmux adapters would slot in beside the others when needed.

**Background sessions** are the exception to all three tiers. The registry's `kind` is `"bg"` (vs `"interactive"`) for sessions the Claude Code daemon runs on its own pty — `claude --bg`, a fork with `--reply-on-resume`, a claimed spare — and they sit in no terminal at all (`claude daemon status` lists the daemon; `claude agents` the sessions). The scanner sets `ClaudeSession.isBackground` and skips the host walk (the daemon is reparented to launchd, so it finds nothing anyway); the overlay groups them under a **Background** header that renders even when it's the only group, sorted after real hosts and before "Other". Clicking such a row runs `TerminalFocus.attachBackground`: it opens a new window in the user's terminal (Ghostty via `new window with configuration` + `initial input`, iTerm2 via `write text`, Terminal.app via `do script` — whichever is running, Terminal.app as the fallback) in the session's cwd, typing `claude attach <jobId>` into the shell so the user's PATH resolves `claude` and Ctrl+Z out of the attach lands in a normal prompt. The id is the registry's `jobId` (`ClaudeSession.attachId` falls back to the first 8 chars of the sessionId). A missing `kind` reads as interactive so an older CLI keeps click-to-focus. `--scan` prints `bg=<id>` on those rows.

Apple events require the `NSAppleEventsUsageDescription` key (in `build-app.sh`'s plist) and a one-time Automation grant per target app. **Ad-hoc signing re-prompts after every rebuild** because TCC keys the grant to the code signature — set `SIGN_IDENTITY` in `.env` for a stable identity. `swift run` (unbundled) gets no prompt and is denied silently, so test this path with the installed `.app`. `--scan` prints each session's `host=` bundle id and `title=` so the matching inputs are inspectable.

## Overlay grouping and the title line

Rows are grouped two levels deep by `SessionHost` (`SessionsView.grouped`, tested): host app ("Ghostty", "VS Code"; daemon-run background sessions under "Background", unresolvable hosts last under "Other") then, for VS Code, the window (label = workspace name; windows the extension hasn't reported yet sort last with no label). Hosts and windows sort by label; sessions inside keep the scanner's (cwd, pid) order, so nothing jumps between polls. The app header renders only when there are two or more apps, or whenever a Background group exists (that header is what explains the missing terminal). A window header shows the window name plus, when every session in it shares a cwd (`WindowGroup.sharedPath`), the path — and those rows then omit it. Sessions in the same window have no divider between them; separate windows (and Ghostty rows, each its own window) do. A Ghostty-style row shows name, then path, then title (italic), then branch. Under a window header the header already names the project, so the row's bold line is the conversation summary instead ("TBD" until `ai-title` exists), the italic line is dropped, and the path is omitted when the header carries it; with two or more sessions in one window that bold line drops from 14 to 12.5 pt so they read as items under the header. Each row also shows the session's `title` (the transcript's `ai-title`, italic caption) under the project name; it's the cheapest thing Claude Code gives us to tell two sessions in one project apart. Other free hints in the transcript, unused so far: `slug` (a memorable per-session name like "vivid-swimming-parnas") and `last-prompt` (the newest user prompt).

## Testing — hand-rolled, on purpose

**This machine has no XCTest or swift-testing** (Command Line Tools toolchain only, no Xcode), and the owner prefers no test-framework dependency. Tests live in `SelfTest.swift` — a tiny assertion runner baked into the binary, run via `swift run ClaudeStatus --self-test`. Do **not** add a `testTarget`, `import XCTest`, or `import Testing`; add cases to `SelfTest.run()` instead. It covers the pure logic (registry parsing, status mapping, dir-name flattening, tail parsing, menubar label, formatting, and the hub's framing, terminal-stream filtering, replay buffer, directory ordering, HTTP/WebSocket parsing, and connection gate); GUI and filesystem paths are exercised via `--scan` and running the app, the hub via a private instance (`CLAUDEANDREW_HOME` + `CLAUDEANDREW_CMD`).

## Things to know before editing

- **Never use `@State`; use `@ViewState`** (`ViewState.swift`). Since the macOS 27 SDK, `@State` is a macro backed by `libSwiftUIMacros.dylib`, which ships only inside Xcode — this machine has Command Line Tools only, so `@State` fails with "plugin for module 'SwiftUIMacros' not found" plus a cascade of "'self' is immutable" errors. `@ViewState` wraps the still-present `State<Value>` struct and behaves like the classic property wrapper (`$binding` works). `build-app.sh` rejects any `@State` in `Sources/`. `@Binding`, `@ObservedObject`, `@StateObject`, `@Environment`, and friends are still plain wrappers and fine. Also `import Combine` explicitly in files using `Timer.publish`/`onReceive` — Swift 6.4 warns when it's only reached through SwiftUI.
- `LSUIElement=true` in `Info.plist` (built inline in `build-app.sh`) plus `setActivationPolicy(.accessory)` keep the app out of the Dock. Don't remove either.
- Signing is best-effort: `SIGN_IDENTITY` from `.env` if the cert exists, else ad-hoc. Unlike ClaudeUsage there are no keychain ACLs at stake, so ad-hoc is fine here.
- The overlay's row order is stable (cwd, then pid) so rows don't jump between 2 s polls — state is conveyed by color, not position. Keep it stable.
- Transcript tail reads are capped at 64 KB and tolerate a truncated first line; entries are one JSON object per line.
