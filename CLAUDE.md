# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ClaudeShip` is a single-target Swift Package macOS menubar app (`Package.swift`, `Sources/ClaudeShip/`). It shows one glyph in the menubar summarizing all running Claude Code sessions — a **green ●** when any session is busy, an **orange ●** when one or more are waiting on user input, and **○** in the system label color when everything is idle (or nothing runs). (The busy glyph was a 32-frame spinner; at 16 fps it cost ~5.5% of a core whenever anything was busy, so it's a still dot now — `CLAUDESHIP_SPINNER=1` brings the animation back.) The glyphs are **drawn with NSBezierPath, not font characters** — the system font lacks U+25D0–25D3, and fallback served the left/right halves and top/bottom halves from different fonts at visibly different sizes. Don't switch back to string glyphs. Clicking it opens a borderless overlay panel listing each session (project, branch, path, state + how long it's held, uptime). The menubar app itself is local inspection: no network, no keychain, no credentials. The one thing that listens on the network is the separate **session hub** — the Rust `claudeship` binary in `hub/` (below) — and only to loopback and the tailnet; the menubar app is its loopback HTTP client.

**Icon.** One drawing, `web/icon.svg` — a starship in Claude's colour (#d97757) whose exhaust is the Claude mark's burst of wedges, on the terminal's near-black — serves every surface: the favicon and the page's brand mark directly, the iPhone icon via `swift ios/make-icon.swift` (rasterizes it with WebKit, corners squared since iOS masks icons), and the Mac bundle's `assets/ClaudeShip.icns` via `./make-mac-icon.sh` (same renderer with `--rounded`, then `iconutil`). Change the SVG, run both scripts. The name is one word, **ClaudeShip**, everywhere.

The build scripts, panel machinery, and visual style are lifted wholesale from `~/Documents/code/claude-usage` (ClaudeUsage) — same borderless `NSPanel` + `NSVisualEffectView` chrome, same animations, same footer idiom. The overlay is **392 pt wide** (vs ClaudeUsage's 280); height follows the SwiftUI content. When restyling, keep the two apps visually in sync.

## Common commands

```bash
./build-app.sh                    # swift build -c release + assemble + codesign → ./ClaudeShip.app
./install.sh                      # build app + hub (unless SKIP_BUILD=1), replace /Applications/ClaudeShip.app, install ~/.local/bin/claudeship, restart the app
swift run ClaudeShip --self-test  # run the hand-rolled test suite (exit 0/1)
swift run ClaudeShip --scan       # headless: print detected sessions and exit — debug the heuristics
swift run ClaudeShip --focus <pid> # headless: raise that session's terminal, print host app/title/outcome
swift run ClaudeShip --host <pid>  # headless: print every app in <pid>'s ancestor chain and which one the walk picks
swift run                          # dev loop (menubar app, unsigned)
```

The hub and the `claudeship` command are Rust (`hub/`, `claude-sessions/`); their commands and tests are in `docs/hub.md`.

## Architecture

`App.swift` → `AppDelegate.swift` → `SessionStore` (single source of truth) drives an `NSStatusItem` and a borderless `PopoverPanel` hosting `SessionsView` (SwiftUI). `SessionStore` polls every 2 s (cheap — all local, plus one loopback request to the hub via `HubClient`); `objectWillChange` is observed by `AppDelegate` to repaint the menubar count (hop one runloop tick because `objectWillChange` fires *before* the `@Published` write).

Detection path — `SessionScanner.swift`, all pure/blocking, called off-main via `Task.detached`:

1. **Live-session registry (the source of truth)** — Claude Code maintains one JSON status file per running process at `~/.claude/sessions/<pid>.json` with `pid`, `sessionId`, `cwd`, `name` (e.g. "claude-status-b3"), `startedAt`/`statusUpdatedAt` (epoch **ms**), and an authoritative `status`. The CLI's status enum (extracted from the 2.1.202 binary) is `["busy","shell","idle","waiting"]`, plus a `waitingFor` detail string. Mapping: busy→green work, shell→user running a `!` command, idle→at the prompt (NOT an alarm state), waiting→orange. Unknown/missing statuses read as idle — never a false alarm color. Files whose pid is dead (`kill(pid, 0)`) are crash leftovers, skipped. The rust app at `~/Documents/code/system-stats` (`src/claude.rs`) reads the same registry and was the reference for this.
2. **Transcript garnish** — the transcript at `~/.claude/projects/<dashed-cwd>/<sessionId>.jsonl` (cwd flattens: every non-alphanumeric/`-` char becomes `-`) is tail-read only for `gitBranch` and mtime. State never comes from transcripts: a first cut inferred it from the last JSONL entry and couldn't distinguish "idle at prompt" from "waiting on permission" — don't regress to that.

`SingleInstance.swift` (flock on `~/Library/Application Support/ClaudeShip/instance.lock`) guards against duplicate menubar items, same rationale as ClaudeUsage. `--self-test`, `--scan`, `--focus <pid>`, and `--host <pid>` dispatch at the top of `App.main`, before NSApplication or the lock. The old `--install-hook`/`--uninstall-hook` flags only print a pointer to `claudeship hub install-hook` and exit 2: the hook belongs to the hub now. `--permission-hook` prints the same pointer but exits 0 with nothing on stdout (`legacyFlagExitCode`, tested): a leftover settings.json entry may still run it, and Claude Code reads a PermissionRequest hook's exit 2 as a deny.

## Session hub (`hub/`, `docs/hub.md`)

The hub — the process that owns the pty of every session started through `claudeship`, the web page, or the phone, and serves the web app and its API — is the Rust binary in `hub/` (the registry/transcript reader it shares with system-stats is `claude-sessions/`). `docs/hub.md` is its architecture, commands, and regression checklist; `docs/rust-core-plan.md` the migration. What the Mac side needs to know:

- **The overlay is an HTTP client** (`HubClient.swift`, Foundation only, synchronous — called from the scanner's off-main task). It reads the hub home (`CLAUDESHIP_HOME`, else `~/Library/Application Support/ClaudeShip/hub`) for `config.json`'s `port` (default 7433) and the pairing secret `token`, and talks to `http://127.0.0.1:<port>` with `Cookie: claude_ship=<token>` — no cookie jar, no proxy, no Origin header (the hub demands a matching Origin only when one is sent). Never log the token. `GET /api/state` (1 s timeout) each poll; `POST /api/kill {id}`, `/api/approve {id, allow}`, `/api/auto-approve {sessionId, rule}` (2 s). No hub answering (not running, no token yet) just means no Virtual group and no approval buttons — every other part of the overlay works from the registry alone.
- **Virtual sessions.** `SessionScanner.scanWithHub` sets `ClaudeSession.hubId` from the state entry with the same (Claude) pid; the hub does the supervisor-ancestry match. Hub sessions group under a **Virtual** header between real hosts and Background; clicking one opens a new terminal window running `claudeship hub attach <id>` (`TerminalFocus.openTerminal`, shared with the Background path). The overlay footer's **"+"** (`AppDelegate.newHomeSession` → `TerminalFocus.openNewSession`) opens a terminal window in the home directory running `claudeship --permission-mode auto` — the Mac's counterpart of the clients' quick "+". Both type `claudeship` into the user's shell, so it must be on PATH (`~/.local/bin`). Right-clicking any row offers **End session** (`AppDelegate.endSession`): hub sessions through `HubClient.kill`, others by SIGHUP to the pid with SIGKILL after 5 s if the registry file is still there. `--scan` prints `hub=<id>` on those rows.
- **Protocol.** `HubClient.protocolVersion` is 3 (the hub's `PROTOCOL`, `web/app.js`, the phone's). A hub stating another version still gets its sessions listed and ended, but approval data from it is ignored (no buttons). Bump it with the hub.
- **Install flow.** `install.sh` needs cargo: `cargo build --release -p claudeship`, then copies `target/release/claudeship` to a temp name beside `~/.local/bin/claudeship` and renames it over (a running hub keeps its mapped binary), runs `claudeship hub install-service` (a LaunchAgent running `claudeship hub run` at login; it prints a restart hint when the running build differs) and `claudeship hub install-hook`. **An install never restarts a running hub** — it owns live sessions. `SKIP_HUB=1` / `SKIP_HOOK=1` opt out. The app bundle no longer contains a hub binary or the web assets (the Rust binary embeds the page).
- **First install after the Swift hub.** The old Swift hub (the bundle's `claudeship-cli`, run as `claudeship hub run`) holds the socket, port, and lock, and nothing stops it automatically. Stop it by hand before that first `./install.sh`, when its sessions can end: `claudeship hub stop` while `~/.local/bin/claudeship` is still the symlink into the old bundle.
- **The web gate's reasons** (implemented in `hub/src/web/security.rs`; don't loosen any check without replacing it with something stronger): loopback talks only to loopback; otherwise the local address must be one a tunnel interface actually holds *and* both ends in Tailscale's ranges — the range alone is ordinary CGNAT space some Wi-Fi networks hand out. The Host header must be `localhost` or a loopback/tailnet IP literal, never a DNS name: over plain HTTP whoever runs the network's DNS can rebind any name to 127.0.0.1 and be same-origin with us, cookie included (`allowedHosts` is the exact-match escape hatch). And the pairing secret, because network position is not a login — other users of the Mac, a sandboxed app, a forwarded port, or a peer on another mesh VPN that also puts 100.64/10 on `utun` all pass the first two. A phone that "can't connect": check `tailscale status --json` for a handshake and bytes from it first (zero bytes = the phone never sent: its Tailscale off, or iOS Local Network permission denied).
- **iPhone app** (`ios/`, its own `CLAUDE.md`): a native SwiftUI client over the same API and WebSocket.

## Remote approval (hub-owned)

When a session hits a permission prompt, the user can approve/deny it from the overlay (and the web page, and the phone) instead of the terminal. The hub owns the whole flow (`docs/rust-core-plan.md` phase 7, `docs/hub.md`):

1. **Hook** — `claudeship hub install-hook` (run by `install.sh`; `SKIP_HOOK=1` opts out) registers a `PermissionRequest` hook in `~/.claude/settings.json` running `claudeship permission-hook`, timeout 86 400 s (a leak backstop, not UX). The merge is surgical and idempotent, and replaces the old Swift helper's `--permission-hook` entry in the same pass.
2. **Helper** (`claudeship permission-hook`) — forwards the request to the hub's `approvals.sock` and blocks with no deadline for one verdict. **The prime directive: emit a decision only on an explicit verdict.** No hub, hang-up, crash, malformed reply — all exit 0 with no output, which Claude Code treats as "no decision" and defers to the terminal prompt. So approvals exist only while the hub runs (the login service sees to that).
3. **Hub** — holds the pendings and the per-session auto-approve rules ("5m" or "session", in memory only, pruned on expiry or session end), reports them in `/api/state` (each session entry's `approvals: [{id, tool, summary, detail, receivedAt}]` and `autoApprove: null | {until: ms} | {session: true}`, top-level `approvalsSupported: true`), and does the reconciliation the app used to: **the terminal prompt and the buttons are live simultaneously**, and when the user answers in the terminal (the registry status leaves `waiting` with a `statusUpdatedAt` newer than the request), the hub drops the pending and closes the helper without a verdict, so nobody talks over an answer already given. Pendings whose session is gone are pruned after 10 s.

**The overlay's part** (`SessionStore.applyHubApprovals`): each poll rebuilds `pendingApprovals` (`PendingApproval`: the hub's id, sessionId, tool, summary, detail, receivedAt) and `autoApprove` from the state, joining the hub's entries to rows by pid (sessionId from the entry, else the registry). Rows with a pending request read as waiting (`effectiveState`), and render Approve / Deny / `⋯` **in place of the status text**, with the hub's summary where the timing caption goes and the full detail as the tooltip. Approve/Deny post `/api/approve`; the `⋯` menu's "Approve all for 5 minutes" / "Approve all for this session" post `/api/auto-approve` with `5m` / `session`, and the row shows a yellow bolt while the hub reports a live rule. A clicked request is hidden at once (`answered`) and stays hidden until the hub stops listing it — its state is cached up to a second — unless the post failed, when the buttons come back. No hub, or one not on protocol 3 with `approvalsSupported`: no buttons, and the terminal prompt is the only way to answer.

## Click-to-focus (raising the session's terminal)

Clicking a row brings that session's terminal to the front (`TerminalFocus.swift`, wired through `SessionsView.onFocusSession` → `AppDelegate.focusTerminal`, which closes the panel first and runs the focus off-main on a serial queue). Two tiers:

1. **Emulator adapters**, chosen by the bundle id of the host app: `hostApp` walks the sysctl `ppid` chain (claude → zsh → login → Ghostty) collecting every ancestor LaunchServices knows as an app and prefers the nearest one with a *regular* activation policy (`chooseHostIndex`, tested), settling for an accessory only when nothing regular is above it. Verified against VS Code: its helpers (`Code Helper (Plugin)` etc., all `com.microsoft.VSCode.helper`, LSUIElement) don't register with LaunchServices at all, so the walk lands on `com.microsoft.VSCode`; the policy preference guards against editors whose helpers do register. **Ghostty 1.3+** has an AppleScript dictionary but exposes no pid/tty, so surfaces are matched on working directory plus the tab title Claude Code sets — the transcript's newest `ai-title` entry, which the scanner now reads alongside `gitBranch` and the store carries forward (`ClaudeSession.title`). Match order: cwd + title, title alone, cwd alone, else fall through. One list round-trip (`ghosttyListScript`), the pick in Swift (`pickGhosttyTerminal`, tested), then `focus terminal id "…"`. **Terminal.app** and **iTerm2** expose a `tty` per tab/session, matched to the pid's controlling tty (`ttyPath`, via `kinfo_proc.e_tdev` + `devname`).
2. **VS Code bridge** (`vscode-extension/`, adapter `.vscode` for VS Code / Insiders / Cursor / VSCodium bundle ids). VS Code has no scripting for terminals, so a vendored extension (plain JS, no build) runs in every window and watches `~/Library/Application Support/ClaudeShip/vscode-focus/request.json`. The app writes `{ts, nonce, pids, cwd, sessionId}` there atomically (`bridgeVSCode`), where `pids` is the session pid's whole ancestor chain (`ancestorPids`); each window compares its terminals' `processId` (the shell pid) against that list — only the owning window matches, which is what makes one shared file work across windows and across several claudes in one window. That window calls `terminal.show()` (selects the exact tab/split) and answers `reply.json` with `{nonce, workspace, terminal}`; the app then raises that window with the editor's bundled CLI (`cliURL`: `<cli> <workspace>` focuses the window that already has it open, never opens a new one), or plain activation when the reply has no workspace (untitled window). No reply within 1.5 s (extension missing, remote window, no match) falls through to tier 3. The extension ignores requests older than 15 s and dedupes by nonce. It also publishes each window's state to `vscode-focus/windows/<env.sessionId>.json` (`{ts, name, workspace, terminals:[{pid,name}]}`) on activation, terminal open/close, and a 30 s heartbeat, removing it on deactivate; the scanner loads those once per scan (`loadVSCodeWindows`, files older than 90 s ignored) and `TerminalFocus.host(of:windows:)` resolves each session's `SessionHost` (app + VS Code window label). `install.sh` packages it with `vscode-extension/pack.sh` (zip + vsix manifest, no npm — a symlink into `~/.vscode/extensions` is *not* picked up) and installs via each editor's CLI that exists on disk; `SKIP_VSCODE_EXT=1` opts out; open windows need one reload after an install. Same folder open in two windows resolves to whichever the CLI picks — the only known inexact case.
3. **Generic fallback**: activate the host app (`NSRunningApplication.activate()`, then `NSWorkspace.openApplication` with `activates` — the cooperative `activate()` can be refused because our panel is non-activating). Right app, whatever tab it was on. Kitty/WezTerm/tmux adapters would slot in beside the others when needed.

**Background sessions** are the exception to all three tiers. The registry's `kind` is `"bg"` (vs `"interactive"`) for sessions the Claude Code daemon runs on its own pty — `claude --bg`, a fork with `--reply-on-resume`, a claimed spare — and they sit in no terminal at all (`claude daemon status` lists the daemon; `claude agents` the sessions). The scanner sets `ClaudeSession.isBackground` and skips the host walk (the daemon is reparented to launchd, so it finds nothing anyway); the overlay groups them under a **Background** header that renders even when it's the only group, sorted after real hosts and before "Other". Clicking such a row runs `TerminalFocus.attachBackground`: it opens a new window in the user's terminal (Ghostty via `new window with configuration` + `initial input`, iTerm2 via `write text`, Terminal.app via `do script` — whichever is running, Terminal.app as the fallback) in the session's cwd, typing `claude attach <jobId>` into the shell so the user's PATH resolves `claude` and Ctrl+Z out of the attach lands in a normal prompt. The id is the registry's `jobId` (`ClaudeSession.attachId` falls back to the first 8 chars of the sessionId). A missing `kind` reads as interactive so an older CLI keeps click-to-focus. `--scan` prints `bg=<id>` on those rows.

Apple events require the `NSAppleEventsUsageDescription` key (in `build-app.sh`'s plist) and a one-time Automation grant per target app. **Ad-hoc signing re-prompts after every rebuild** because TCC keys the grant to the code signature — set `SIGN_IDENTITY` in `.env` for a stable identity. `swift run` (unbundled) gets no prompt and is denied silently, so test this path with the installed `.app`. `--scan` prints each session's `host=` bundle id and `title=` so the matching inputs are inspectable.

## Overlay grouping and the title line

Rows are grouped two levels deep by `SessionHost` (`SessionsView.grouped`, tested): host app ("Ghostty", "VS Code"; daemon-run background sessions under "Background", unresolvable hosts last under "Other") then, for VS Code, the window (label = workspace name; windows the extension hasn't reported yet sort last with no label). Hosts and windows sort by label; sessions inside keep the scanner's (cwd, pid) order, so nothing jumps between polls. The app header renders only when there are two or more apps, or whenever a Background group exists (that header is what explains the missing terminal). A window header shows the window name plus, when every session in it shares a cwd (`WindowGroup.sharedPath`), the path — and those rows then omit it. Sessions in the same window have no divider between them; separate windows (and Ghostty rows, each its own window) do. A Ghostty-style row shows name, then path, then title (italic), then branch. Under a window header the header already names the project, so the row's bold line is the conversation summary instead ("TBD" until `ai-title` exists), the italic line is dropped, and the path is omitted when the header carries it; with two or more sessions in one window that bold line drops from 14 to 12.5 pt so they read as items under the header. Each row also shows the session's `title` (the transcript's `ai-title`, italic caption) under the project name; it's the cheapest thing Claude Code gives us to tell two sessions in one project apart. Other free hints in the transcript, unused so far: `slug` (a memorable per-session name like "vivid-swimming-parnas") and `last-prompt` (the newest user prompt).

## Testing — hand-rolled, on purpose

**This machine has no XCTest or swift-testing** (Command Line Tools toolchain only, no Xcode), and the owner prefers no test-framework dependency. Tests live in `SelfTest.swift` — a tiny assertion runner baked into the binary, run via `swift run ClaudeShip --self-test`. Do **not** add a `testTarget`, `import XCTest`, or `import Testing`; add cases to `SelfTest.run()` instead. It covers the pure logic (registry parsing, status mapping, dir-name flattening, tail parsing, menubar label, grouping, formatting, auto-approve rules, and `HubClient`'s parsing of `/api/state` and `config.json`); GUI and filesystem paths are exercised via `--scan` and running the app. `HubClient` against a live hub: run the Rust hub privately (`CLAUDESHIP_HOME` with its own `port` + `CLAUDESHIP_CMD`) and the app with the same `CLAUDESHIP_HOME`. The Rust hub has its own tests (`cargo test`, which is fine there; the no-framework and `@ViewState` rules are for this Swift package).

## Things to know before editing

- **Never use `@State`; use `@ViewState`** (`ViewState.swift`). Since the macOS 27 SDK, `@State` is a macro backed by `libSwiftUIMacros.dylib`, which ships only inside Xcode — this machine has Command Line Tools only, so `@State` fails with "plugin for module 'SwiftUIMacros' not found" plus a cascade of "'self' is immutable" errors. `@ViewState` wraps the still-present `State<Value>` struct and behaves like the classic property wrapper (`$binding` works). `build-app.sh` rejects any `@State` in `Sources/`. `@Binding`, `@ObservedObject`, `@StateObject`, `@Environment`, and friends are still plain wrappers and fine. Also `import Combine` explicitly in files using `Timer.publish`/`onReceive` — Swift 6.4 warns when it's only reached through SwiftUI.
- `LSUIElement=true` in `Info.plist` (built inline in `build-app.sh`) plus `setActivationPolicy(.accessory)` keep the app out of the Dock. Don't remove either.
- Signing is best-effort: `SIGN_IDENTITY` from `.env` if the cert exists, else ad-hoc. Unlike ClaudeUsage there are no keychain ACLs at stake, so ad-hoc is fine here.
- The overlay's row order is stable (cwd, then pid) so rows don't jump between 2 s polls — state is conveyed by color, not position. Keep it stable.
- Transcript tail reads are capped at 64 KB and tolerate a truncated first line; entries are one JSON object per line.
- **Resting CPU.** The 2 s scan is cheap because transcript tails are cached by mtime (`SessionScanner.cachedTail`) — a session that isn't writing costs nothing to re-scan — the process ancestry and host app of each pid are cached for its life (`SessionScanner.ancestry`, keyed on the registry's `startedAt` against pid reuse; the sysctl walk plus LaunchServices lookups were the next most expensive step), and the busy glyph is a still dot (glyph bitmaps are cached in `AppDelegate.glyphCache`; `updateStatusItemTitle` skips a repaint of the glyph it already shows). The store publishes only when something the overlay shows changed (`SessionStore.sameForDisplay` ignores `lastActivity`, the transcript mtime, which moves every scan while a session is busy), and the overlay's 1 s clock runs only while the panel is open (`store.panelVisible`). Measured: ~0.1% of a core with a busy session and the panel closed. `CLAUDESHIP_SPINNER=1` re-enables the old animation.
- **The hub request.** `HubClient.state()` is one loopback GET per 2 s poll, on the scanner's background task, 1 s timeout; the hub caches `/api/state` for a second. With no hub running it costs a refused connection.
